# Presentation Design

Use [the presentation standard](references/presentation-design-standard.txt) for
composition and review. It is also a portable instruction document that may be
attached to a presentation brief in another application.

## Inputs and authority

Identify the audience, purpose or decision, source material, output application,
and requested length from the conversation. Ask only for material gaps. A user's
explicit layout direction, approved template, and current brand profile take
precedence over the fallback editorial method. Preserve layouts the user likes.

Keep organization-specific colors, logos, fonts, private source documents, and
approved example decks outside this generic skill. Read the supplied brand
profile and use exact tokens with their intended roles. If sources conflict,
prefer explicitly approved current guidance and disclose unresolved ambiguity.
Never present a guessed palette as the organization's brand.

## Compose and produce

1. Map the source into a slide sequence. Give each slide a takeaway, supporting
   evidence, layout choice, and source reference. For a small edit, work directly
   on the affected slides instead of generating an unnecessary full brief.
2. Choose composition by meaning: a table for comparison, a chart for quantity,
   a timeline for sequence, or typographic rows for risks and decisions. Maintain
   hierarchy and alignment without turning every idea into a boxed card.
3. Apply the supplied brand's background, text, graphic-accent, and readable-accent
   roles. Verify the actual foreground/background pairs; do not rely on color
   alone to communicate status. Keep the logo as an approved asset.
4. Use the user's requested application and its available creation/editing tools.
   For an application demo, keep the demonstrated creation in that application.
   If a required capability is unavailable, deliver the brief and exact prompt,
   and identify the remaining creation step rather than silently substituting
   a different workflow.
5. Inspect every affected rendered slide for content integrity, hierarchy,
   readability, overflow, and unintended overlap. Verify native editability for
   tables/charts where required. Save and reopen when the application permits;
   otherwise describe precisely what was inspected and what remains unverified.

Do not restart generation while the prior operation may still be running.
Preserve a failed or partial result and its status before retrying. A successful
completion message is not evidence that the saved deck renders correctly.

## Portable handoff

When preparing a shared knowledge package, supply the standard, a separate
organization brand profile, and available approved templates/examples. Keep the
project brief and factual source documents with the project. Use relative file
names or links the destination can access, not machine-local paths.

A reference document carries guidance; it does not by itself install a native
skill, configure an agent, or grant deck-editing capabilities. Verify the actual
file reference and creation flow in the destination application before claiming
that the handoff works. Report local creation, upload, retrieval, and rendered
verification as separate outcomes.
