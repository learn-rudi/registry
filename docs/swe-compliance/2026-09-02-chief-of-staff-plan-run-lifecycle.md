## Phase 2: Behavioral Contract And Failure Design

**Status: complete**

- `plan.json` remains the sole portable authority; `runs/*.json` remains
  noncanonical transport.
- A run revision may equal or lag the plan revision, but may never lead it.
- Lag is accepted only when the complete run remains semantically consistent
  with current plan identity, node lifecycle, immutable attempt bindings,
  histories, locks, reconciliations, and result references.
- Every accepted run write catches `run.planRevision` up to the currently
  validated plan revision.
- Reconciliation owns both halves of its cross-file invariant: the accepted
  plan reconciliation and the matching attempt `resultReference`.
- Plan is written first and run second. An interruption after the plan write
  produces a recognizable safe lag; exact replay repairs only the missing run
  reference/revision without creating another plan revision.
- Stale, conflicting, ambiguous, run-ahead, or otherwise inconsistent state
  fails closed and preserves the owned file bytes.
- Cancellation follows the same persisted-reference and replay rules, including
  cancellation before dispatch where no attempt reference exists.
- No new dependency is permitted. The implementation uses the existing lock,
  validation, deterministic serialization, fsync, and atomic-replace machinery.
- Exit criterion: the behavior is expressible through public CLI tests without
  weakening the closed-schema or authority boundaries.

  `validate-run` accepts; run lifecycle writes then catch up.

  run state; exact replay repairs a simulated plan-first interruption.
