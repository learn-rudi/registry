# ADR 0002: Editorial Markup Stack And Skill Boundary

## Status

Accepted

## Context

Inline editorial markup starts as an agent workflow: a user supplies draft text, a transcript, or extracted source text, and the agent proposes visible deletions, insertions, and notes for review. The generated artifact must then behave like product software: it needs deterministic rendering, accept/reject state, clean-copy export, source-model inspection, screenshot QA, and scroll/layout verification across desktop and mobile viewports.

RUDI already separates executable capability bundles from editable workflow guidance. Registry stacks expose MCP tools through `provides.tools`; registry skills remain editable Markdown playbooks installed under `~/.rudi/skills`. Existing stack-related-skill support lets a stack declare companion workflows through `related.skills` without confusing instructions with executable tools.

## Decision

Create a first-class `stack:editorial-markup` for deterministic artifact construction, validation, export, and visual QA. Keep `skill:inline-editorial-markup` as the editorial workflow layer that tells an agent when to use the stack, how to form edits, when to add notes, and when to ask the human for approval.

The stack should expose these tools:

- `editorial_markup_validate_model`: validate paragraph/change/note shape, unique IDs, status values, and clean-export readiness.
- `editorial_markup_build`: render static or interactive HTML from a validated source model and write artifacts outside the public catalog tree.
- `editorial_markup_qa`: run browser smoke tests, capture desktop/tablet/mobile screenshots, and assert intended vertical and horizontal scroll behavior.
- `editorial_markup_export_clean`: produce clean text from an explicit resolved edit state.

Proposal generation remains a skill-led workflow until a real adapter exists. If a future `editorial_markup_propose` tool is added, it must call an explicit configured agent or LLM command and validate the resulting `edit_model` before rendering.

The stack core accepts normalized text inputs:

- `source_text` for small and medium drafts.
- `source_path` for large local text/Markdown/HTML inputs.
- `source_manifest` for multi-section or chunked sources.
- `edit_model` for agent-generated or user-supplied proposed edits.

Non-text sources are normalized before this stack runs: media should use audio or video transcription stacks, and URLs should use content extraction stacks. The editorial-markup stack may preserve source metadata, but it should not become the default media or web extraction layer.

Direct `source_text` input should be bounded. The initial contract is:

- prefer `source_path` or `source_manifest` when text is too large for chat or a single tool call;
- accept inline `source_text` up to a documented stack limit;
- chunk proposal work by section for long sources;
- split artifacts or render section navigation when a single interactive page would exceed practical review size.

For implementation, start with conservative defaults: direct `source_text` around 200,000 characters, proposal chunks around 6,000 to 8,000 characters, and sectioned or multi-artifact output when sources exceed about 100,000 characters or the edit model exceeds about 250 changes. These limits are operational guardrails, not product promises; the stack should return structured validation errors when callers exceed them.

Visual QA is part of the stack contract. Interactive HTML builds must verify JavaScript syntax, required controls, accept/reject/reset/accept-all/copy-clean flows, screenshot capture at desktop/tablet/mobile viewports, absence of unintended body-level horizontal overflow, independent desktop document/sidebar scrolling, and explicit horizontal scrolling for source-model panels and narrow mobile toolbars.

## Consequences

Users get a first-class executable workflow without losing editable agent instructions. Installing the stack can offer or link the related skill through `related.skills`, and installing the skill declares the stack dependency through `requires.stacks`.

The stack treats LLM or agent output as untrusted input. Any proposal generated by `editorial_markup_propose` must pass the same model validation as external caller input before rendering. Generated runtime state, screenshots, clean exports, and QA artifacts belong under a caller-provided output directory or RUDI runtime state, never under the public catalog package.

The initial implementation should not duplicate existing extraction stacks. It should compose with audio, video, and content-extractor stacks for non-text sources, then own the editorial markup artifact lifecycle after text is available.
